# Claude Code 云端服务化方案分析

## 1. 背景与文章结论

参考文章：阿里云开发者《Claude code云端部署 & 魔改sdk实现http流式调用保姆级教程》

文章要解决的问题可以归纳为三类：

1. Claude Code 原本是本地 CLI 产品，需要能在云端、沙箱或无外网环境中部署。
2. CLI 输出不适合作为业务系统调用能力，需要转换成 HTTP + 流式结构化响应。
3. Claude Code 的状态、记忆、配置、会话历史都与文件和进程强相关，多用户共享实例会产生串扰风险。

文章提出的主方案是：

1. 使用 `npm pack` 或离线包方式安装 Claude Code。
2. 使用 Python SDK + FastAPI + SSE 包装 `query()` 和多轮会话能力。
3. 将 Node.js、Claude Code、Python HTTP 服务打进基础镜像。
4. 用“一用户一沙箱 + 用户文件快照版本化”做运行时隔离和持久化。

这套思路适合我们启动 Axiom 的第一版，但实现策略需要做两点校准：

1. 优先封装官方 SDK 和 CLI headless/stream 输出能力，避免一开始就魔改 SDK。
2. 把沙箱控制面、状态快照和权限策略作为产品核心能力，而不是部署脚本的附属功能。

## 2. 我们要做的产品定义

Axiom 的目标不是“把 Claude Code 放到服务器上跑起来”，而是做一个可复用的云端 Agent 执行底座：

1. 业务系统通过 HTTP 调用一个用户专属的 Agent 工作区。
2. Agent 能流式返回执行过程、工具调用、最终结果和错误。
3. 每个用户、项目或任务都有独立状态，互不污染。
4. 沙箱可以销毁和重建，用户的工作目录、记忆、配置、会话历史可恢复。
5. 后续可以接入不同 Agent runtime，而不把业务 API 绑死在 Claude Code 私有细节上。

建议北极星指标：

1. 首次可用响应耗时：冷启动和热启动分别统计。
2. 流式首 token 时间。
3. 任务成功率：HTTP 请求到最终结果完成。
4. 状态恢复成功率：沙箱回收后重新进入同一工作区能否恢复文件和上下文。
5. 隔离事故数：跨用户文件、会话、凭据串扰必须为 0。

## 3. 推荐目标架构

```text
Client / Business App
        |
        v
API Gateway
        |
        v
Axiom Control Plane
  - authentication
  - workspace routing
  - sandbox allocation
  - lifecycle management
  - snapshot orchestration
  - audit log
        |
        v
Sandbox Runtime Pool
  - Claude Code CLI / SDK
  - Axiom Agent HTTP Service
  - workspace filesystem
  - restricted network and tool policy
        |
        v
Persistent State Layer
  - object storage snapshots
  - metadata database
  - session and request records
  - secret manager
```

核心分层：

1. Control Plane：负责“哪个用户请求路由到哪个沙箱”，不直接执行 Agent 任务。
2. Runtime Service：运行在沙箱内，负责把 Agent runtime 包成统一 HTTP/SSE 接口。
3. Snapshot Service：负责工作区文件、Claude 配置、会话状态的打包、差异上传、恢复和回滚。
4. Policy Layer：负责权限、工具、网络、文件范围、敏感信息输出控制。

## 4. MVP 范围

第一阶段只做能验证核心假设的最小闭环。

必须做：

1. 单用户单沙箱的 HTTP 流式调用。
2. `POST /v1/query/stream`：输入 prompt，返回 SSE 事件。
3. 沙箱内固定工作目录，例如 `/workspace`。
4. 请求级日志：request_id、workspace_id、耗时、退出状态、错误摘要。
5. 最小快照：请求结束后打包 `/workspace` 和必要的 Claude 配置目录。
6. 手动恢复：从指定快照恢复工作区。

暂缓：

1. 多轮会话池。
2. 多租户沙箱池自动扩缩容。
3. 增量快照。
4. Web 控制台。
5. Hook、Subagent、MCP 的完整远程配置。
6. SDK 魔改。

MVP 验证问题：

1. 官方 SDK 或 CLI headless 模式是否足够支撑稳定流式响应？
2. Claude Code 运行所需状态文件有哪些，快照恢复后是否完整可用？
3. 冷启动耗时是否能接受？
4. 权限策略是否能避免无人值守执行卡死，同时不放大安全风险？

## 5. HTTP 接口草案

### 5.1 单次查询

```http
POST /v1/query/stream
Content-Type: application/json
Accept: text/event-stream
```

请求：

```json
{
  "workspace_id": "ws_123",
  "prompt": "分析当前项目并给出改造建议",
  "model": "default",
  "cwd": "/workspace",
  "allowed_tools": ["Read", "Grep", "Glob"],
  "metadata": {
    "user_id": "user_123",
    "request_source": "api"
  }
}
```

SSE 事件建议：

```text
event: message_start
data: {"request_id":"req_123"}

event: content_delta
data: {"type":"text","text":"..."}

event: tool_call
data: {"tool":"Read","status":"started"}

event: tool_result
data: {"tool":"Read","status":"completed"}

event: final
data: {"status":"completed","usage":{}}

event: error
data: {"code":"runtime_error","message":"..."}
```

### 5.2 快照管理

```http
POST /v1/workspaces/{workspace_id}/snapshots
POST /v1/workspaces/{workspace_id}/restore
GET /v1/workspaces/{workspace_id}/snapshots
```

第一版可以只支持全量 tarball。增量快照等验证性能瓶颈后再做。

## 6. 状态隔离设计

文章中“一用户一沙箱 + 文件版本化”的判断是正确方向。我们建议把隔离粒度从 `user_id` 扩展成 `workspace_id`：

1. 一个用户可能有多个项目，项目之间也应该隔离。
2. 一个项目可能有多个任务分支，后续可以演进到 `workspace_id + branch_id`。
3. 权限、快照、审计都绑定 workspace 更清晰。

需要纳入快照的路径：

1. `/workspace`：用户项目文件和 Agent 产物。
2. Claude Code 相关配置目录：需要在实测后列白名单。
3. 项目级配置文件，例如 `CLAUDE.md`、`.claude/`。

不应纳入快照的内容：

1. API key、访问令牌、云厂商凭据。
2. 缓存、临时文件、依赖目录，例如 `node_modules`、`.venv`、构建产物。
3. 系统级日志。

建议快照元数据：

```sql
CREATE TABLE workspace_snapshots (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  workspace_id VARCHAR(64) NOT NULL,
  version INT NOT NULL,
  storage_key VARCHAR(512) NOT NULL,
  checksum VARCHAR(128) NOT NULL,
  file_count INT,
  total_size BIGINT,
  created_by_request_id VARCHAR(64),
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uniq_workspace_version (workspace_id, version),
  INDEX idx_workspace_created_at (workspace_id, created_at)
);
```

## 7. 关键风险

### 7.1 魔改 SDK 风险

文章强调“基于 FastAPI 重写或魔改 SDK”。这适合验证，但不适合作为长期架构起点：

1. SDK 更新后维护成本高。
2. 私有对象结构变化会导致事件序列化失效。
3. 很难保证权限、安全和兼容性。

建议：第一版只用官方公开 API；确实缺能力时，先做适配层隔离，再评估是否 fork。

### 7.2 权限绕过风险

文章提到默认使用 `bypassPermissions` 避免无人值守卡死。这个点要谨慎：

1. 生产环境不应默认绕过所有权限。
2. 必须用 workspace 级文件边界、工具白名单、网络策略兜底。
3. 高危工具和外部命令需要显式授权或运行在更严格沙箱里。

建议：MVP 使用最小工具白名单，只允许读文件、搜索、必要的编辑操作；执行命令单独配置。

### 7.3 多用户状态串扰

不能依赖应用层 session_id 隔离。只要复用同一个进程、同一个 home 目录、同一个工作目录，就有串扰风险。

建议：生产设计坚持每个活跃 workspace 独占 runtime home 和 workspace filesystem；热池复用前必须清理并重新加载快照。

### 7.4 快照一致性

Agent 执行过程中可能边写文件边触发快照，导致不一致。

建议：

1. 请求完成后快照。
2. 主动关闭沙箱前快照。
3. 空闲回收前快照。
4. 后续增加文件锁或 copy-on-write 目录。

### 7.5 成本与冷启动

一 workspace 一沙箱隔离强，但成本和启动耗时更高。

建议：

1. MVP 先接受冷启动。
2. 第二阶段做 warm pool。
3. 第三阶段做快照增量恢复和镜像预热。

## 8. 第一阶段任务拆分

### P0：验证 Runtime Service

1. 建立 Python FastAPI 服务。
2. 封装官方 Claude Code SDK 或 CLI stream 输出。
3. 实现 `POST /v1/query/stream`。
4. 定义统一 SSE 事件结构。
5. 加入 request_id、错误事件、心跳和超时。

验收标准：

1. curl 可以收到连续 SSE 事件。
2. 异常会返回结构化 `error` 事件。
3. 请求结束有 `final` 事件。

### P0：验证快照恢复

1. 定义 workspace 目录。
2. 请求结束后生成 tarball。
3. 新建空目录后恢复 tarball。
4. 验证恢复后再次请求能读取上次生成的文件。

验收标准：

1. 文件内容一致。
2. 快照带 checksum。
3. 敏感文件不会进入快照。

### P1：Control Plane 原型

1. 根据 workspace_id 分配本地 runtime 进程或容器。
2. 维护 workspace 到 runtime 的映射。
3. 支持手动释放 runtime。
4. 支持健康检查。

验收标准：

1. 同一 workspace 连续请求命中同一 runtime。
2. 不同 workspace 使用不同 home/workspace 目录。
3. 释放后可从快照恢复。

### P1：镜像化

1. 构建基础镜像。
2. 固定 Node.js、Python、Claude Code 版本。
3. 容器启动自动拉起 Runtime Service。
4. 暴露 `/healthz` 和 `/docs`。

验收标准：

1. 镜像可在无交互环境启动。
2. 启动后 health check 通过。
3. 可通过 HTTP 调用一次完整任务。

## 9. 技术选型建议

默认栈：

1. FastAPI：Runtime Service 和 Control Plane 都可先用 Python 实现。
2. SSE：第一版比 WebSocket 更简单，适合单向流式输出。
3. SQLite/PostgreSQL：本地原型用 SQLite，服务端用 PostgreSQL。
4. 本地文件 tarball：MVP 快照先写本地目录，后续替换为 OSS/S3。
5. Docker：先容器隔离，后续再接云沙箱平台或 Kubernetes。

## 10. 立即下一步

建议从最小可运行骨架开始：

1. 创建 `runtime_service`。
2. 加 `POST /v1/query/stream`，先用 mock 流验证 SSE 协议。
3. 再接入 Claude Code 官方 SDK 或 CLI stream。
4. 创建 `snapshot_service`，实现全量快照和恢复。
5. 写端到端脚本：创建 workspace -> 调用 query -> 生成文件 -> 快照 -> 恢复 -> 再查询。

这样可以在不陷入沙箱平台选型和 SDK 魔改细节的情况下，最快验证最重要的闭环。
