## 2. 候选输入规范化

### 2.1 ServiceKey

ServiceKey 规范文本为：

```text
namespace + "/" + group + "/" + serviceName
```

三个字段已由公共 API 限制为 ASCII 名称字符，不再转小写。`Topo-Service` 和 `topo-service` 是两个不同服务。

### 2.2 AffinityKey

1. 输入按 Unicode NFC 归一化。
2. 不 trim、不转大小写、不对数字做十进制重写。
3. UTF-8 长度必须为 1–256 字节。
4. 禁止 Unicode General Category `Cc`、`Cf` 和非字符 code point。
5. affinity key 只在请求内存中存在，不写日志、指标 label、路由诊断响应或磁盘。

### 2.3 候选实例

进入算法前按以下顺序过滤：

1. 保留与请求 ServiceName 完全一致的实例。
2. 保留 Registry 全局状态为 `UP` 的实例；`SUSPECT`、`DOWN`、`RECOVERING` 均不参与新请求。
3. 移除 `SelectionRequest.excludedInstanceIds`。
4. 移除当前 JVM 本地状态为 `OPEN` 的实例。
5. `HALF_OPEN` 实例只在获得唯一探测许可后可参与，普通 `select()` 不选它。
6. 按 instanceId ASCII 升序产生稳定输入数组。

算法不得依赖 Registry 返回的 JSON 顺序、Map 迭代顺序或 JVM identity hash。过滤后为空时抛 `NoAvailableInstanceException`。

## 3. 规范哈希字节

对 serviceKey、affinityKey 和 instanceId 三个 UTF-8 字节串分别做长度前缀，然后连接：

```text
u32be(serviceKeyUtf8.length)  || serviceKeyUtf8
u32be(affinityKeyUtf8.length) || affinityKeyUtf8
u32be(instanceIdUtf8.length)  || instanceIdUtf8
```

`u32be` 是 4 字节无符号大端整数。不使用分隔符拼接，避免字段边界歧义。哈希函数固定为 SHA-256，不使用平台默认 Charset、`String.hashCode()`、UUID hash 或随机 seed。

```java
static byte[] canonicalBytes(
        String serviceKey,
        String affinityKey,
        String instanceId
) {
    ByteArrayOutputStream output = new ByteArrayOutputStream(512);
    writeLengthPrefixedUtf8(output, serviceKey);
    writeLengthPrefixedUtf8(output, affinityKey);
    writeLengthPrefixedUtf8(output, instanceId);
    return output.toByteArray();
}
```

## 4. 加权 Rendezvous Hash

### 4.1 分数公式

1. 计算 SHA-256 digest。
2. 把 digest 前 8 字节视为无符号大端 64 bit 整数 `raw`。
3. 取 `mantissa = raw >>> 11`，得到 53 bit 非负整数。
4. 计算 `u = (mantissa + 1.0d) / (2^53 + 1.0d)`，保证 `0 < u < 1`。
5. 计算 `score = -StrictMath.log(u) / weight`。
6. score 越小排名越靠前。

weight 是 1–10,000 整数。使用 `StrictMath.log`，不使用 `Math.log`、float、BigDecimal 近似或本地 native 向量函数。

### 4.2 比较器

```text
Double.compare(scoreA, scoreB)
  → 平局时比较 instanceId ASCII 升序
```

非法 weight 在模型入口已被拒绝。如果仍出现 NaN、Infinity 或重复 instanceId，视为目录不变量破坏，不向业务返回任意选择。

### 4.3 主选和备选

对全部候选实例计算一次 score 并完整排序。`CandidatePlan` 在一次逻辑调用内固定 ServiceSnapshot revision 和排序数组；重试不重新读快照、不重新计算主选。

## 5. 黄金哈希向量

固定输入：

```text
serviceKey = customer-a-prod/DEFAULT_GROUP/topo-service
instances  = node-a(weight=100), node-b(weight=200), node-c(weight=50)
```

### 5.1 affinityKey=topo-42

| instanceId | SHA-256 | u | score |
| --- | --- | --- | --- |
| `node-a` | `a0f312278f0b1f9b97aa7393c2621987685c335ddbf51187e89cf953c9de1e3a` | `0.62870896783628571` | `0.0046408681960023587` |
| `node-b` | `67230e53f26a26474883387c2eec4e250a672b2aa31d024766a3750503366731` | `0.40287866162763258` | `0.0045455992507205086` |
| `node-c` | `28a47933be296adf69d351c439ad6da2c8eab59c2652c82e1820819ce9499391` | `0.15875966561558183` | `0.036807275145907092` |

确定性顺序必须是：

```text
node-b → node-a → node-c
```

单元测试必须精确断言 digest 和顺序。u/score 只作诊断，允许最多 2 ULP 的断言容差。

### 5.2 多键顺序

| affinityKey | 确定性顺序 |
| --- | --- |
| `topo-001` | `node-b → node-c → node-a` |
| `topo-002` | `node-a → node-b → node-c` |
| `topo-003` | `node-c → node-a → node-b` |
| `中文-拓扑-7` | `node-b → node-a → node-c` |

Unicode 向量同时验证 UTF-8 和 NFC 归一化。测试还必须使用分解与预组合等价字符，断言归一化后顺序相同。

### 5.3 权重分布向量

只使用 `node-a(weight=1)` 和 `node-b(weight=3)`，affinityKey 从 `key-000000` 到 `key-099999`，使用本文完整规范计算：

```text
node-a = 24,906
node-b = 75,094
```

黄金测试精确断言上述计数；性质测试另断言 1:3 权重下比例误差不超过 1 个百分点。

## 6. 节点变更与最小迁移

1. 移除一个实例时，原主选不是该实例的 key 主选不得变化。
2. 新增一个实例时，只有新实例 score 优于原主选的 key 发生迁移。
3. 实例恢复为 `UP` 后，新请求按原算法自然迁回；正在进行的 CandidatePlan 不改变。
4. 权重修改视为新目录 revision，只影响修改后创建的 CandidatePlan。

性质测试使用至少 100,000 个 key，严格断言移除节点后的非必要迁移数为 0。

## 7. 无 affinity 的加权最少并发

对实例 i 的比较值为：

```text
(activeRequests_i + 1) / weight_i
```

实现不使用浮点除法，使用交叉乘法比较 A 与 B：

```text
(activeA + 1) * weightB  compareTo  (activeB + 1) * weightA
```

`activeRequests` 使用非负 long，交叉乘法使用 `Math.multiplyExact`；如果溢出则回退到 BigInteger 比较，不允许溢出回绕改变排序。

最小比值平局时，先按 instanceId 升序得到 ties，再用每个 ServiceKey 的 `AtomicLong tieSequence` 做 `floorMod(sequence, ties.size())`。tieSequence 是 JVM 本地公平性状态，不要求跨 JVM 一致。

固定向量：

| instance | weight | activeRequests | 比值 |
| --- | ---: | ---: | ---: |
| `node-a` | 100 | 99 | 1 |
| `node-b` | 200 | 199 | 1 |
| `node-c` | 50 | 0 | 0.02 |

第一次必须选 `node-c`。移除 node-c 后，连续四次平局选择必须是 `node-a, node-b, node-a, node-b`。

## 8. 并发许可和 SelectionLease

1. 选择后使用实例级 `Semaphore.tryAcquire(remainingDeadline)` 获得许可。
2. 获取失败时可尝试 CandidatePlan 的下一实例，但总等待时间不超过 `acquire-timeout` 且仍受整体 deadline 约束。
3. 许可成功后 activeRequests +1，`SelectionLease.close()` 仅释放一次并使 activeRequests -1。
4. 任何异常路径、BodyHandler 错误和请求取消都必须关闭 lease。activeRequests 小于 0 是不变量违反，必须 ERROR 报警并在测试中失败。
5. 如果所有候选都达到上限，抛 `OverloadedException`，不创建无界排队。

## 9. affinity key 提取

提取优先级固定为：显式 API → Header → Path 变量 → Query → JSON Pointer。路由只能配置一种自动来源；显式 API 值存在时不再读取 Body。

| 来源 | 规则 |
| --- | --- |
| Header | 名称大小写不敏感，多值时拒绝，不用逗号合并 |
| Path | 使用已解码的路由变量，不在 SDK 内重新匹配 URL |
| Query | 必须恰好一个值，`+` 不当作空格除非上层已按 form 规则解码 |
| JSON Pointer | 遵循 RFC 6901，只接受 string/number/boolean 标量，数字使用 JSON 原始规范文本 |

配置了自动来源但未提取到值时，默认抛出 `AFFINITY_KEY_MISSING`，不静默降级为无亲和策略。只有路由显式配置 `on-missing: USE_NON_AFFINITY` 时才允许降级。

## 10. Target URI 解析

```text
target = instance.baseUri.resolve(request.path + encodedQuery)
```

解析前必须验证：

1. request path 是以 `/` 开头的 absolute-path，不含 scheme、authority、fragment、反斜杠或 NUL。
2. 对每个 path segment 做一次 percent decode 后，`.`、`..` 和包含 `/`/`\` 的结果必须拒绝。
3. query 只由结构化参数编码，不将用户原始 query 与 baseUri 拼接。
4. resolve 后的 scheme、host 和 port 必须与 baseUri 完全一致，否则抛 `UnsafeTargetUriException`。
5. DNS 解析由 HttpClient 与配置的安全策略处理；SDK 不接受请求级代理和 Host 覆盖。

## 11. deadline 和重试顺序

### 11.1 deadline

逻辑调用开始时记录 `startedNanos = System.nanoTime()`，计算 `deadlineNanos = saturatedAdd(startedNanos, timeoutNanos)`。每个阶段只读剩余预算：

```text
remaining = max(0, deadlineNanos - System.nanoTime())
```

选址、获取许可、连接池、DNS、连接、TLS、请求传输、响应、BodyHandler、退避和重试都消耗同一 deadline。任何重试不得重置 timeout。

### 11.2 幂等判定

| 请求 | 是否可重试 |
| --- | --- |
| GET、HEAD、OPTIONS | 是 |
| PUT、DELETE | 仅在存在 idempotencyKey 时 |
| POST、PATCH | 仅在存在 idempotencyKey 且业务路由声明服务端支持幂等时 |

无响应时若请求不可重试，连接在写出任意 Body 字节后中断必须抛 `IndeterminateWriteException`。

### 11.3 失败分类

| 失败 | 默认重试 | 本地失败计数 |
| --- | --- | --- |
| 建连拒绝/路由不可达 | 幂等时切换下一候选 | 是 |
| 连接超时 | 幂等时切换下一候选 | 是 |
| 等待响应超时 | 仅明确幂等时 | 是 |
| TLS 证书/主机名错误 | 否 | 否，属于安全配置错误 |
| HTTP 429 | 默认否 | 否 |
| HTTP 5xx | 默认否 | 否 |
| Body 解码错误 | 否 | 否 |
| 本地获取许可超时 | 尝试下一候选 | 否 |

HTTP 状态码重试必须由路由级白名单显式开启，首版默认集合为空。

### 11.4 退避

```text
base = 25ms
cap = 250ms
exponential = min(cap, base * 2^(attempt - 1))
delay = deterministicUniform(0, exponential, requestId + attempt)
```

为使故障重放测试可重复，jitter 使用 requestId 和 attempt 的 SHA-256 前 53 bit 映射，不使用全局 Random。如果 `delay + minimumAttemptBudget > remaining`，不睡眠且结束重试。退避必须使用可注入 Scheduler/Clock，单元测试不执行真实 sleep。

## 12. 本地隔离状态机

| 状态 | 入口 | 出口 |
| --- | --- | --- |
| `CLOSED` | 初始或探测成功 | 连续 3 次可归因失败后进入 OPEN |
| `OPEN` | 连续失败达阈值 | 单调冷却 20s 后进入 HALF_OPEN |
| `HALF_OPEN` | 冷却结束 | 1 个探测成功进 CLOSED，失败进 OPEN |

1. 只有连接拒绝、路由不可达、连接超时和等待响应超时增加连续失败。
2. 成功完成 HTTP 响应 Header 即重置连续传输失败，不以业务状态码判定网络健康。
3. 冷却时间使用 `System.nanoTime()` 抽象，不用 Instant。
4. OPEN 不写 Registry，不改变 ServiceSnapshot，不影响其他 JVM。
5. 实例从目录删除后本地状态延迟 5 分钟清理，避免短时目录抖动丢失隔离历史。
