# 数据、本体与导入设计

## 1. 存储职责

```text
SQLite：唯一权威事实源
Qdrant：可重建的章节语义索引
```

SQLite 保存“什么事实当前成立、由谁证明”；Qdrant 只回答“用户问题语义上像哪些章节”。Qdrant 损坏、迁移或更换 Embedding 模型后，必须能从 SQLite 中的当前章节完整重建。

## 2. SQLite 逻辑数据模型

第一期无需 RDF 或图数据库。普通关系表和索引即可支持四跳遍历。

```text
documents
- document_id                 稳定业务 ID
- source_key                  唯一，例如 team.md
- title
- content_hash
- updated_at

sections
- section_id                  稳定语义 ID
- document_id
- heading_path_json
- summary
- content
- source_start_line
- source_end_line

concepts
- concept_id                  全局稳定 ID
- name
- concept_type
- definition

concept_aliases
- concept_id
- alias
- alias_kind                  canonical / query

section_concepts
- section_id
- concept_id
- role                        primary / mentioned / rule_subject

relations
- relation_id
- from_concept_id
- relation_type
- to_concept_id

relation_evidence
- evidence_id
- relation_id
- document_id
- section_id
- source_quote
- source_hash

vector_index_jobs
- job_id
- source_key
- operation                   upsert / delete
- status                      pending / processing / succeeded / failed
- retry_count
- error_message
```

建议建立唯一约束：

```text
documents(source_key)
sections(section_id)
concepts(concept_id)
concept_aliases(concept_id, alias)
relations(from_concept_id, relation_type, to_concept_id)
relation_evidence(relation_id, document_id, section_id, source_hash)
```

## 3. 本体关系与推理

关系本身绑定稳定概念，不绑定 Markdown 标题或版本：

```text
member_invitation --creates--> pending_invitation
pending_invitation --governed_by--> seat_billing
invitation_link_expired --exception_of--> member_invitation
```

`relation_evidence` 记录文档和章节为什么支撑这条边。关系有效条件为：至少存在一条当前文档 Hash 对应的证据。多文档同时支撑时，替换其中一个文件只影响该文件的证据。

Java `OntologyReasoner` 采用确定性规则：

| 关系 | 自动扩展 | 作用 |
| --- | --- | --- |
| `creates` | 是 | 由动作找到状态，再找状态规则。 |
| `requires` | 是 | 补充前置条件。 |
| `governed_by` | 是 | 补充计费、权限、限制等管辖规则。 |
| `exception_of` | 是 | 将异常问题连接到主功能规则。 |
| `overrides` | 是 | 排除被新规则覆盖的内容。 |
| `parent_of` / `has_part` | 否 | 归类和概念定位。 |
| `related_to` | 否 | 弱候选关系，不直接进入上下文。 |

限制：最多四跳、最多八个新增概念、最多三份关联文档。第三、四跳只能进入重排序候选，不能跳过重排序直接给回答模型。

## 4. Qdrant Collection

一个 collection 对应一个 Embedding 模型和维度：

```yaml
collection: product-knowledge-v1
embeddingModel: <gateway-provided-chinese-multilingual-model>
dimensions: <model-returned-dimension>
distance: Cosine
```

每个 section 一个 point。向量化输入：

```text
文档标题
章节路径
章节摘要
概念名称、canonical aliases、query aliases
章节正文
```

payload 最小化：

```json
{
  "sectionId": "team_member_management.invitation_link_expired",
  "documentId": "team_member_management",
  "sourceKey": "team.md",
  "conceptIds": ["member_invitation", "invitation_link_expired"],
  "embeddingModel": "<model-id>"
}
```

Qdrant 不保存权威正文、关系或发布状态。查询返回 `sectionId` 后必须回 SQLite 确认章节仍属于当前 `source_key` 和 `content_hash`。

更换模型或维度时：创建新 collection，从 SQLite 全量向量化，完成验证后切换配置；禁止在一个 collection 中混写不同模型的向量。

## 5. 手动导入

接口：

```http
POST /api/admin/knowledge-imports
Content-Type: application/json

{"sourceKey":"team.md"}
```

执行顺序：

```text
1. 仅接受内部运维身份或部署侧服务密钥调用；浏览器插件不能调用。
2. 服务端校验 `sourceKey` 是受限的相对 Markdown 文件名（拒绝绝对路径、`..`、分隔符和非 `.md` 后缀），再从固定可信目录读取 team.md 与 team.knowledge.json。
3. 检查文件对、source.key、SHA-256、JSON Schema、ID 和 evidence quote。
4. 以 `source_key + content_hash` 作为幂等键；同一已完成导入返回已有结果。
5. 开始 SQLite 事务。
6. 删除 team.md 旧 sections、section_concepts 和 relation_evidence。
7. 写入新 document、sections、concepts/aliases、relations 和 relation_evidence。
8. 删除没有剩余 evidence 的 relation。
9. 提交 SQLite 事务。
10. 创建 Qdrant delete / upsert 同步任务。
```

步骤 4 仅删除当前 `source_key` 拥有的数据。全局概念可继续被其他文档引用；关系仅在其全部 evidence 消失后才失效。

## 6. 同步与删除

Qdrant 同步采用最终一致性：

```text
SQLite 成功 + Qdrant 成功：IMPORTED
SQLite 成功 + Qdrant 失败：IMPORTED_WITH_INDEX_PENDING
SQLite 失败：IMPORT_FAILED
```

失败任务按退避策略重试。索引未完成时，后端不得用旧向量回答新版本内容，应返回 `knowledge_updating`。

显式删除：

```http
DELETE /api/admin/knowledge-sources/team.md
```

删除 SQLite 中该源拥有的章节和关系证据，再异步删除相应 Qdrant point。一次处理目录时未出现某文件，不触发删除。
