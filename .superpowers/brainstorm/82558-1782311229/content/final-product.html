编排怎么做

我们采用固定业务节点而不是通用自由编排：前端用 React Flow 负责画流程和配置，后端用 FastAPI + Celery 执行 DSL、调度模型、回写证据链，保证流程可控、可审、可回放。

技术选型与难点说明

一页讲清：我们怎么做、为什么这么选、怎么解决难点。

推荐技术栈

  • 前端：React + TypeScript + React Flow
  • 后端：Python FastAPI
  • 任务：Redis + Celery
  • 存储：PostgreSQL + 磁盘 / NAS
  • 检索：pgvector，后续可替换专业向量库
  • 模型：统一模型网关接入 LLM / OCR / VL / Embedding / Rerank / Parser

版本策略

  • 演示版：模板管理 + 指标管理 + 知识录入 + 图谱审核 + 校验 + 报告
  • 最终版：补齐日志、监控、模型、编排、问答、广场、权限、审计
入口文件 + 模板 + 知识库
结构解析标题树、字号、表格、页眉页脚
指标约束必填 / 选填 / 条件必填
规则判定硬规则 + 软规则 + 人工复核
输出结果问题、依据、原因、建议、Trace

怎么克服难点

  • 不让模型直接拍板，用规则引擎做最终判定
  • 模板不直接转图谱，先转指标，再生成候选图谱
  • 知识库录入保留证据链、chunk、审核版本，避免无依据
  • 编排与应用分离，前端用画布复用，执行层自己掌控

为什么能落地

  • 先做单文档校验闭环，避免一开始范围过大
  • 文件先落磁盘/NAS，简化首期交付
  • 模型与业务解耦，便于后续替换和路由
  • 日志、监控、审计统一打通，便于运维

一句话结论

用于汇报
产品定位

做一个面向软件说明文档的模板约束驱动平台，先完成校验闭环，再平台化扩展。

核心能力

模板管理、指标管理、知识库治理、图谱审核、文档校验、模型管理、日志监控、智能体广场。

技术原则

模型负责识别，规则负责判定，人工负责审核，平台负责留痕与分发。

选型关键词
React Flow FastAPI Celery PostgreSQL pgvector NAS 模型网关 规则引擎
难点 1 模板如何生成可执行指标和候选图谱，而不是直接把文档丢给模型。
难点 2 文档如何稳定解析成结构树，再把结构树映射到指标和规则。
难点 3 模型、日志、监控、广场和编排如何统一成一个可运营的平台。
