技术选型与难点说明

一页讲清：我们怎么做、为什么这么选、怎么解决难点。

最终技术栈

  • 前端：React + TypeScript + React Flow
  • 后端：Python FastAPI
  • 任务：Redis + Celery
  • 存储：PostgreSQL + 磁盘 / NAS
  • 检索：pgvector，后续可替换专业向量库
  • 模型：统一模型网关接入 LLM / OCR / VL / Layout / Embedding / Rerank / Parser

为什么这么选

  • React Flow 适合做流程和拓扑画布
  • FastAPI 适合承载校验、治理和模型调度服务
  • Redis + Celery 适合跑文档解析、图谱生成和校验任务
  • PostgreSQL + pgvector 足够承载业务数据、图谱关系和检索索引
  • 磁盘 / NAS 先满足文档存储，不强依赖 MinIO

最终结论

  • 模型负责抽取，规则负责校验，证据链负责解释，人工审核负责兜底。
  • 系统原型页用功能拓扑表达模块关系，技术说明页用模型链路、校验链路和编排策略解释实现路径。
  • 平台先把文档校验闭环跑通，再扩展到知识库问答和智能体广场。

技术说明

模型选型 / 校验路径 / 编排策略

1. 文档结构怎么抽出来

推荐模型链路
  • PDF / DOCX：优先走文档解析器，保留段落、样式和字体信息。
  • 扫描件 / 图片：先 OCR，再做版面检测和阅读顺序恢复。
  • 复杂版式：补一层 VL 模型做标题、表格、图文关系识别。
  • 最终由 parser 汇总成结构树、标题树和证据链。
哪些模型负责什么
  • OCR：识别图片里的文字与位置，适合扫描版文档。
  • Layout / PPK / 版面模型：判断块级区域、标题层级、表格和段落边界。
  • VL 模型：处理复杂页面，辅助判断标题、表格、图文组合和阅读顺序。
  • Parser：把上述结果转成统一 JSON / Markdown 结构。
字号与标题层级怎么来
  • DOCX / PDF 原生文本：字号优先来自文件元数据和 span 样式，不靠猜。
  • 扫描件：字号通常不是直接读出来，而是根据标题层级、版面位置和字体粗细做推断。
  • 推断结果必须带置信度和证据页码，低置信项进入人工审核。
稳定性怎么保证
  • 模板先拆成指标，再限制模型只能在指标范围内抽取。
  • 每个抽取结果都要回写来源文件、页码、段落或坐标。
  • 图谱先生成候选版本，再进入人工审核和编辑。

2. 文章怎么校验

1. 选模板 用户选择模板和对应指标集，校验范围和必填项立即确定。
2. 抽结构 系统先识别标题、字号、章节顺序、表格、图片和选填段落，再生成结构树。
3. 对指标 规则引擎把结构树映射到模板指标，判断缺失、顺序错误、字号不符和内容约束不符。
4. 出结论 最终输出哪里错了、为什么错了、依据是什么，并附上证据链和定位信息。

3. 为什么 Dify / n8n 只作为参考

  • 我们参考它们的交互表达、节点化编排和可视化体验，而不是照搬业务执行层。
  • Skill、MCP 等思路可以帮助我们组织能力边界，但核心校验、证据链和模板约束必须可控。
  • 文档校验是强规则、强审计、强证据链的场景，所以执行层需要自定义，前端和编排层可以吸收成熟产品经验。

4. 模型选择汇总

能力适用输入输出说明
OCR扫描件 / 图片 / PDF 图片层文字、框坐标、页级块负责从图片中把字读出来，是扫描版文档的第一步。
Layout / 版面模型PDF、图片、混合版式文档标题块、段落块、表格块、阅读顺序更擅长判断版面结构，帮助识别标题层级和区域边界。
VL 模型复杂排版、图文混排、样式不稳定文档语义结构、标题意图、图文关系用于补足 OCR 和 Layout 的不确定性，特别适合复杂页面。
Parser / 规则解析器OCR / Layout / VL 的中间结果统一结构树、Markdown、证据链把多路结果合并成平台可消费的标准结构。

5. 证据链怎么落地

来源定位每个抽取结果都保留文件、页码、段落或坐标，便于追溯。
解释输出校验结论同时输出规则命中信息和原文片段，便于复核。
人工审核低置信项进入人工确认，保证图谱和结论都能被编辑和修正。
