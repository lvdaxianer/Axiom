# 设计文件智能体技术方案

- **日期**：2026-06-25
- **状态**：草案
**目标**：面向多类型模板文档的校验、知识治理、模型管理、日志监控和智能体编排，构建一套可配置、可审核、可追溯的设计文件智能体平台。

---

## 1. 背景与目标

客户的文档模板类型很多，软件设计说明、软件需求规格、标准化工作报告、产品文档、接口设计文档等都存在不同的结构要求、字号要求、标题层级要求和内容约束。

这类场景的核心难点不是“能不能读文档”，而是：

1. 如何让模型稳定地识别模板要求，抽出结构图谱。
2. 如何在校验时，基于模板图谱判断文档哪里错了、为什么错了、依据是什么。
3. 如何把模型、规则、证据链、人工审核和流程编排串成一个闭环。

因此，本方案采用“模板指标先行、模型抽取、规则校验、证据留痕、人工审核兜底”的总体思路。

---

## 2. 总体方案

平台分为两条主线：

### 2.1 模板治理主线

客户录入模板后，系统先把模板解析成指标集合，再在指标约束下生成模板图谱。

图谱不是直接信任模型一次性输出，而是：

- 模型先生成候选图谱
- 平台根据指标进行约束校验
- 人工可编辑、可审核、可确认
- 审核通过后形成正式模板图谱

### 2.2 文档校验主线

用户选择某个模板图谱后，系统对待检文档进行结构识别，并按照图谱和指标做逐项校验。

输出结果必须包含三类信息：

- 哪里错了
- 为什么错了
- 依据是什么

## 3. 产品能力划分

### 3.1 日志与运行监控

系统要以用户维度保留日志，管理员可以查看全部日志。

主要日志类型包括：

- 操作日志
- 知识库录入日志
- 文件审核日志
- 模型调用日志
- 流程发布日志

监控能力包括：

- 服务健康状态
- 模型健康状态
- 任务队列状态
- 解析任务耗时和失败率
- 审核任务耗时和失败率

### 3.2 指标管理

指标管理是平台的前置约束层。

模板不能直接丢给模型自由生成图谱，而是要先把模板要求拆成指标，例如：

- 必须有哪些章节
- 哪些章节允许选填
- 标题字号应该是多少
- 标题层级如何排列
- 哪些内容是条件必填
- 哪些术语必须一致

指标的作用是限制模型的自由度，让抽取更稳定、更可控。

### 3.3 知识库治理

每个用户可以创建多个知识库，知识库有权重。

知识库管理的核心不是“存文档”，而是把模板、指标、图谱、证据链统一治理起来。

主要能力包括：

- 模板录入
- 指标绑定
- 图谱生成
- 图谱人工审核
- 证据链保留
- chunk 管理
- 知识版本管理

### 3.4 模型管理

模型管理负责统一管理平台接入的模型能力，包括：

- OCR 模型
- VL 模型
- Layout / 版面模型
- Embedding 模型
- Rerank 模型
- Parser / 文档解析模型
- 大语言模型

模型管理不仅是“注册模型”，还要支持：

- 模型路由
- 降级策略
- 版本切换
- 健康检查
- 调用统计
- 停用开关

### 3.5 智能体流程编排

编排层负责把“开始节点、文档校验节点、知识库节点、人工确认节点、输出节点”串起来。

这个层面可以参考 Dify、n8n 的交互表达、节点化组织方式和可视化体验，但核心业务执行层必须由平台自定义掌控。

原因是文档校验属于强规则、强审计、强证据链场景，不能只依赖通用编排工具的默认语义。

### 3.6 知识库问答构建

知识库不仅服务文档校验，也可以扩展到问答构建。

用户可以选择知识库，构建面向业务问题的问答应用，并进行发布。

### 3.7 智能体广场

智能体广场用于统一展示已发布的智能体和知识问答应用。

用户可以在广场里直接运行，形成“编排 -> 发布 -> 运行”的完整链路。

## 4. 技术架构

### 4.1 总体分层

平台建议分为四层：

1. 表达层：系统原型、流程编排、智能体广场
2. 业务层：模板管理、知识库治理、文档校验、日志监控、模型管理
3. 能力层：OCR、VL、Layout、Embedding、Rerank、LLM、Parser
4. 存储层：业务库、向量检索、文件存储、证据链存储

### 4.2 关键链路

#### 模板图谱生成链路

模板录入 -> 指标解析 -> 模型候选抽取 -> 图谱候选生成 -> 人工审核 -> 正式图谱

#### 文档校验链路

文档上传 -> 模板选择 -> 结构抽取 -> 规则匹配 -> 证据整理 -> 审核结论输出

#### 发布运行链路

智能体编排 -> 配置校验 -> 发布 -> 广场展示 -> 用户运行

## 5. 文档结构抽取方案

文档结构抽取的目标不是只识别文本，而是恢复“结构、样式、层级、证据”。

### 5.1 输入类型

- PDF
- DOCX
- 扫描图片
- 混排图片文档

### 5.2 推荐模型链路

#### DOCX / 原生 PDF

优先走文档解析器，直接读取：

- 段落
- 样式
- 字号
- 标题层级
- 表格
- 页眉页脚

这类文件如果带原生结构信息，字号和样式优先来自文件元数据，不应先依赖模型猜测。

#### 扫描件 / 图片

优先走 OCR，再叠加版面检测和阅读顺序恢复。

OCR 负责把字识别出来，版面模型负责判断块级结构、标题块和段落块，VL 模型负责补足复杂页面的语义理解。

#### 复杂排版 / 图文混排

补一层 VL 模型，用于识别：

- 标题意图
- 图文关系
- 表格区域
- 阅读顺序
- 复杂页面中的结构边界

### 5.3 各模型职责

| 能力 | 适用输入 | 输出 | 作用 |
| --- | --- | --- | --- |
| OCR | 扫描件、图片、PDF 图片层 | 文字、框坐标、页级块 | 负责把图片里的字读出来 |
| Layout / 版面模型 | PDF、图片、混合版式 | 标题块、段落块、表格块、阅读顺序 | 负责判断页面结构边界 |
| VL 模型 | 复杂排版、图文混排 | 语义结构、标题意图、图文关系 | 负责补足 OCR 和布局模型的不确定性 |
| Parser | OCR / Layout / VL 的中间结果 | 统一结构树、Markdown、证据链 | 负责把多路结果汇总成标准结构 |

### 5.4 字号与标题层级怎么判断

这里要分两种情况：

#### 原生文档

字号优先从文件元数据、span 样式、段落样式中直接读取。

#### 扫描件

字号通常不是直接读出来的，而是通过以下信号推断：

- 标题层级
- 版面位置
- 字体粗细
- 与上下文的结构关系

推断结果必须带置信度，并保留页码、段落或坐标，方便人工复核。

## 6. 文章校验方案

文档校验不是简单比对文本，而是“结构 -> 指标 -> 规则 -> 证据”的完整流程。

### 6.1 校验步骤

1. 选择模板
2. 载入模板指标
3. 抽取文档结构
4. 把结构映射到指标
5. 规则引擎判定
6. 输出结论与证据

### 6.2 主要校验维度

- 结构是否完整
- 标题层级是否正确
- 章节顺序是否正确
- 字号是否符合模板要求
- 必填内容是否缺失
- 选填内容是否越界
- 术语是否统一
- 表格、图片、附录是否符合模板要求

### 6.3 输出要求

每条校验结果都要输出：

- 问题位置
- 问题类型
- 规则依据
- 原文证据
- 修正建议

## 7. 图谱生成与审核方案

这是本平台最关键的治理部分。

### 7.1 为什么不能直接让模型生成最终图谱

因为模板类型很多，而且每类模板的要求都不一样。

如果直接让模型对整份文件自由抽图谱，会有以下问题：

- 容易漏关系
- 容易乱补关系
- 容易把推断内容当事实
- 容易在不同模板之间漂移

### 7.2 解决办法

采用“指标约束 + 候选图谱 + 人工审核”的方式：

1. 先把模板要求拆成指标
2. 模型在指标约束内生成候选图谱
3. 系统强制检查图谱是否覆盖所有关键指标
4. 人工审核、补充、修正
5. 审核通过后保存正式图谱

### 7.3 图谱必须保留的内容

- 节点定义
- 节点关系
- 指标绑定
- 证据来源
- 版本号
- 审核状态

## 8. 为什么 Dify / n8n 只作为参考

我们不是简单地“不用它们”，而是把它们作为参考对象。

### 8.1 参考的部分

- 节点化交互
- 流程编排表达
- 可视化体验
- 组件组织方式

### 8.2 不直接照搬的部分

文档校验是业务强约束场景，需要平台自己掌握：

- 模板指标
- 图谱审核
- 证据链
- 规则引擎
- 审计留痕
- 模型路由

所以编排可以借鉴通用工具的表达方式，但执行层必须自定义。

## 9. 技术选型建议

### 9.1 前端

- React
- TypeScript
- React Flow

理由：

- 适合做流程画布和功能拓扑
- 适合快速搭建可编辑、可点击、可发布的界面

### 9.2 后端

- Python FastAPI

理由：

- 适合做模型调度和文档处理接口
- 适合承接异步任务和业务编排

### 9.3 异步任务

- Redis
- Celery

理由：

- 适合跑解析、抽取、图谱生成、校验等异步任务

### 9.4 存储

- PostgreSQL
- pgvector
- 磁盘 / NAS

理由：

- PostgreSQL 足够支撑业务数据和图谱关系
- pgvector 可先满足向量检索
- 文档和附件先用磁盘或 NAS，不强依赖 MinIO

### 9.5 模型接入

统一模型网关接入：

- LLM
- OCR
- VL
- Layout
- Embedding
- Rerank
- Parser

## 11. 风险与控制

### 11.1 模型抽取不稳定

控制方式：

- 指标约束
- 候选图谱
- 人工审核
- 低置信度回退

### 11.2 校验解释不清

控制方式：

- 所有结果必须带证据链
- 所有规则必须可追溯
- 所有推断必须带置信度

### 11.3 编排能力过度通用化

控制方式：

- 只借鉴 Dify / n8n 的表达方式
- 执行层保留自定义能力
- 核心业务节点由平台控制

---

## 12. 一句话总结

本平台的核心不是“让模型看懂文档”，而是“让模型在模板指标约束下稳定抽取结构，再由规则引擎基于证据链完成文档校验与审核闭环”。
